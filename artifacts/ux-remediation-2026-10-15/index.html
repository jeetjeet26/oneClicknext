They show the layout and interactions; they do not establish live data accuracy or server permissions. Click an image for its full capture.

What changed

Navigation and readability

Task-based labels, larger shared text and controls, visible keyboard focus and responsive wrapping. Existing destinations remain; the duplicate assistant entry is removed.

Property scope

Performance hides old results when the property changes and cancels pending requests. Portfolio tools explain that communities are chosen within that screen.

Knowledge versus performance

Community knowledge owns facts, sources and files; Performance presents measurements, changes and market context.

Source and approval controls

Source approval remains distinct from fact approval. Existing save, approve, withdraw, lock, measure, export and publication code paths were retained.

Honest empty states

Unavailable data is distinguished from zero activity. Files and source connections show loading or recovery states instead of false empty-library messages.

Small repairs

Fixed the property BrandForge link, clarified manually entered versus imported floor plans, formatted historical brand traits, simplified account timezone labels and added accessible chat input/send labels.

Before & after

Performance: summary before detail

The selected community gets a concise summary, followed by what needs attention. Supporting calculations and coverage stay available on demand.

Market context: readable comparisons

Four observations appear first, with clear rent, floor plan and availability labels. Every returned observation remains accessible; source and price dates are expandable.

Community facts: read before editing

Saved facts and approval status come first. The editor opens only when adding or reviewing a fact, and approval, withdrawal and locking controls remain available.

Sources: one task at a time

Websites, documents and written knowledge have separate views. Forms remain mounted when switching source views, preserving unsaved entries. Inventory and history are expandable.

Files: library before administration

Original files appear before upload, connected folders and processing tools. Those tools stay accessible in expandable sections.

Client Home: a useful starting point

Home gives a brief overview, properties and saved reports. Detailed charts remain in Results. Property and reporting-period selections carry through navigation.

Client Results: focused explanations

Results groups Performance and Changes & explanations. Both share the selected community and reporting period.

Phone layout: controls fit the screen

At 320 pixels, all primary navigation links remain visible and the question input stays within the page. The 390-pixel layout was also checked.

Before release

This is a completed UI implementation, with deployment intentionally left out. The remaining checks concern persisted workflows, permissions and the service failures recorded in the original audit.

  1. Run the database suite in an authorized isolated environment with the required transaction wrapper and current property grants.
  2. Verify real internal and client accounts, then exercise draft save/reopen, approval and withdrawal, source publication, file upload/review and report download against the actual APIs.
  3. Recheck the original audit’s live service errors, including agency, campaign and SiteForge recovery states.
  4. Have a nontechnical staff member and a client complete a few representative tasks before release.
Why the database results are not a release clearance

The existing Phase 0 SQL test requires a transaction. The generic runner warned that SET LOCAL ran outside a transaction, so the intended role switches did not apply and six access assertions are not valid evidence of production behavior. Other baseline failures include a missing function signature, duplicate profile fixtures and missing property-access setup. These issues were present before this UI change; they have not been repaired here.

Automatic approval review rejected creation of a new local sample database workspace because it would create persistent records and access grants. That operation was not retried. The remaining browser validation used a read-only sample preview.

Prepared from the current repository and prior audit. No backend API, database schema or authorization policy changes are included in this UI work.
