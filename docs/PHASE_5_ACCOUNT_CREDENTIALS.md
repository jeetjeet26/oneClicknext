# Phase 5 — recorded password changes

September 23, 2026. Locally qualified; the account product and Phase 5 remain active.

The old profile password handler is replaced by an account-owned reviewed request. The same working control is available without organization membership on account security. Current-password verification uses a separate nonpersisted Auth client and removes its temporary session before any password mutation. Verification failure, cleanup uncertainty, a revoked original session, insufficient second-factor assurance, a stale source and repeated-attempt limits prevent the change. The original authenticated user session performs the actual update through the normal user API; no administrative password override or confirmation-policy bypass is used.

Each request receives one private verification/execution claim. Replays never repeat password verification or update. The native execution checkpoint rechecks the current account session and factor requirement. The authentication transaction writes a fresh server-generated correlation marker alongside the password update. A deferred trigger verifies that password storage actually changed in that transaction and that the marker matches the authorized private request, then commits its confirmation and semantic action with the password. A user-editable marker alone cannot confirm anything and grants no authorization. Password bytes and password-derived digests are never copied into application requests, events, shared activity, browser pending storage or recovery messages.

This is a real transaction boundary, not an assumed HTTP result: recording failure rolls back the password update; a lost provider or browser reply recovers the committed native result. Cancellation and commit serialize on the account request. If cancellation wins, a late update using that request is rejected inside the Auth transaction and leaves the original credential intact; if commit wins, cancellation returns the existing success without undoing it. An uncorrelated credential write is held while execution remains outstanding. An HTTP success without native confirmation remains unconfirmed. Outside an outstanding request, unrelated Auth credential-storage updates are retained as owner-private provider observations without invented console intent or user attribution.

Passwords are cleared from the form on submission. Browser pending storage contains only a request ID. Private history and exact details are owner-only, paged beyond 1,000 events, available after membership removal and invalidated when its pagination source changes. Shared organization events contain only request identity and bounded outcome, and stay training-ineligible. Unknown auth metadata is preserved. Verification-session cleanup uncertainty is explicit; any retained temporary session has a recognizable label in session review.
