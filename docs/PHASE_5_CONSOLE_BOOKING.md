# Phase 5 — console booking and confirmation recovery

Qualified locally September 16, 2026. Initial console booking now saves the reservation, lead/CRM handoff, relevant follow-up stops, attributed activity, confirmation queue and shared action event in one transaction. Stable request identity recovers a lost response. Competing reservations respect shared manual/widget capacity and configured multi-booking slots. Advanced lead state and an existing CRM processing lease are preserved. Recording failure rolls back the reservation and related work.

The booking dialog uses the property timezone, checks a future time within 90 days, rejects skipped/repeated clock-change times and supports explicit setup when the timezone is missing. Initial setup cannot silently overwrite a valid configured timezone; its action is recorded. The dialog retains failed requests, reports current recovered status and shows confirmation queued/paused/review/accepted truthfully. It no longer says a confirmation was sent merely because a booking saved.

Requested confirmations reuse the per-channel reminder recovery protocol. Email and text have separate attempts, pinned content/sender/recipient, provider IDs, explicit review, bounded timely retry and no automatic retry after ambiguous transport. Confirmations are eligible immediately even for a tour several days away, but expire after 23 hours or the tour start. Old bookings without an explicit queue record are not backfilled. The existing reminder schedule processes the new queue; no new provider connection or schedule was activated. Provider acceptance does not establish recipient receipt.

Confirmation emails keep a calendar attachment with an exact UTC start derived from property-local time, a stable event identity and saved timestamp. Calendar preview/download links now use the same resolved instant and duration, holding unknown/ambiguous times rather than using the application host timezone. The confirmation copy uses known schedule facts; the old direct grouped sender and its unchecked personalized-email path are no longer used by console booking. Other existing callers remain for separate qualification.

Verification: 59 service/API cases, 54 new plus 92 reminder rollback-only database assertions, three new booking browser journeys plus three existing reminder journeys. Full type checking passes; targeted lint has zero errors and seven existing leads-page warnings. Local database advisors remain at 1,386 existing WARN/ERROR findings, with none added. Desktop/mobile screenshots were inspected. Fixtures were removed. Evidence: `work/console-booking/` in the development task.

The migration was applied only to the local database without migration-history writes. Delivery remains paused. No hosted migration, provider send, deployment, commit, push or model training occurred. Remaining TourSpark scope includes schedule/calendar delivery recovery, legacy/provider qualification, additional public/automated/interaction recording and real-client acceptance. Other products and later phases remain open.
