# Platform qualification tools

`python3 -m unittest discover -s scripts/platform -v` runs offline tool tests.

`drift.py capture --source production --project-ref <verified-project-ref> --output <snapshot.json>` executes a fixed read-only catalog query with the installed Supabase CLI. macOS may ask to unlock the CLI token in the login keychain. Do not place credentials in arguments or artifacts.

`drift.py capture --source local --output <snapshot.json>` reads the local console container. `--database phase6_<name>` supports isolated rehearsal databases. Captures include public/private columns, RLS, grants, roles, function overloads/security/definition hashes, policies, constraints, indexes, triggers, enums, extensions, default grants, sequence definitions and exact migration-history hashes. Storage policies and auth/storage triggers are included; managed auth/storage table internals, role passwords, sequence values, provider settings and client rows are excluded.

`drift.py compare --baseline <baseline.json> --candidate <candidate.json> --output <report.json>` returns exit 2 on differences, 1 on invalid evidence and 0 on matching structure. Different query versions must be recaptured. Local equality never certifies hosted readiness. Schema hashes are change detectors, not a semantic SQL proof; ACL ordering and managed-version differences are conservatively reported.

`drift.py bundle --snapshot <production.json> --history-dir <verified-cli-fetch-directory> --pending-dir supabase/migrations --pending-manifest <explicit-file-sha256-list.json> --output <new-review-directory>` prepares an offline release review bundle. Historical versions and recorded SQL are verified exactly. It never applies SQL, repairs migration history, links a project or infers equivalence from migration names. All preflight checks complete before output is created. The current fetched-history format has one statement per migration; other shapes fail for review.

A snapshot hash detects accidental changes, not a cryptographic signature of authority. Keep provenance and project identity with the captured evidence. Captured metadata is internal operational evidence. Owner release approval, fresh drift/preflight, product gates and upgrade/restore qualification are still required. Never blindly push reconstructed repository migration history.


`recording.py --root <platform> --functions <current-function-catalog.json> --output <coverage.json>` builds static per-action references, not a production completeness certificate. `lineage.sql` and `privacy.sql` are content-free aggregate queries; the latter is only a heuristic. Read PHASE_6_RECORDING_RETENTION.md before interpreting a zero count.

`datasets.py manifest` prepares synthetic, metadata-only frozen selections; `baseline` freezes exact existing-model source contracts. Neither calls a provider, exports production data nor starts training. `retention.py plan/finish` freezes scoped metadata/deletion lineage and refuses incomplete or stale receipts; it has no hosted erasure executor. Keep actual Storage/database/provider/backup obligations separate.

`operations.py inventory --root <platform>` records configured route hashes. Its `qualify` command checks a supplied observation window; it never runs a scheduler and cannot authenticate arbitrary supplied receipts. Held operation cannot pass. `lock-dependencies.py` prints dependency hashes; `--compile` deliberately recompiles under the qualified Python/pip-tools versions.


## Repeatable production-schema upgrade rehearsal

`rehearsal.py prepare --platform <platform-directory> --baseline <reviewed-baseline.json> --bundle <verified-release-bundle> --output <new-plan.json>` freezes the exact inputs for an isolated local upgrade. It validates the production project, recorded historical SQL, pending migration bytes in both bundle and repository, baseline file hashes, seed and all eligible SQL suites. Test additions or changes require preparing a new plan. The dedicated ReviewFlow response suite retains the generic runner's default `separate_approval_pending` exclusion; neither a modified plan nor a different filename grants execution scope. This label is not its current qualification result: the unchanged suite passed 35 assertions in a separately authorized isolated invocation, recorded in `docs/PHASE_5_REVIEWFLOW_RESPONSE_QUALIFICATION.md`. Old plans and default discovery were not rewritten.

`rehearsal.py run --plan <plan.json> --database phase6_rehearsal_<unique-name> --output <new-evidence-directory>` rechecks the inputs, verifies the local Docker/Supabase project, creates a new database from template0, restores the reviewed schema-only baseline, inserts synthetic legacy rows, applies only the pending migrations, checks preserved legacy values, seeds isolated local fixtures and runs the eligible transaction tests. It then checks for an empty migration history and compares the resulting catalog with the qualified candidate. A failing assertion, truncated/failed pgTAP result, nonzero command, changed source, unexpected catalog difference or existing target makes the run fail. Previous databases and evidence are never reset or overwritten. The command never changes the active `postgres` database, links a project, sends provider requests or applies migration history.

The baseline descriptor is internal release-review material. It has `formatVersion: 1`, `scope: reviewed_schema_only_local_rehearsal`, a `limitations` list, and these relative file paths, each covered by the descriptor's `sha256` map: `snapshot`, `expectedCandidate`, `managedArchive`, `managedList`, `publicSchema`, `privateSchema`, `managedHooks`, `legacyFixture`, `legacyCheck`. Its `contentHash` uses the same canonical digest as the drift tool. `snapshot` must be the production snapshot used by the release bundle; `expectedCandidate` must be an already qualified isolated local catalog. The managed archive/list use the qualified local Supabase runtime; public/private definitions and custom auth/storage hooks come from the reviewed production capture. Record managed-runtime differences explicitly. The archive is always restored with `--schema-only`, without `--create` or `--clean`. Review supplied SQL/archive definitions before execution; hashes detect changes and are not an authorization signature or a sandbox for untrusted SQL.

The runner records the exact Docker image/container identity, per-step timing/log hashes, passed and unrun suites, input hashes and final catalog. A failed database is retained for investigation; use a new target for another trial. Its successful status is `eligible_local_checks_passed`, with `wholePhaseAcceptance: pending`. It cannot certify provider/client acceptance, month-long observation, model quality or client-specific erasure. The normal reconstructed development reset in CI is a separate regression path and must not be labeled a production upgrade.

The reviewed September 24 baseline and plan are retained under `/Users/jasjitgill/Documents/Codex/2026-09-12/we-x20/work/phase6-closeout/`. Production dumps are not added to source control. Reuse that exact baseline/bundle only while a fresh production comparison and source-hash checks still support it. Prepare a new reviewed baseline when production changes; never make a stale snapshot look current by rewriting its metadata.

## Phase 8 paid-pilot and demand review

`npm run review:agency:demand -- template --output <new-program-draft.json>` creates an empty program, with no client, currency, period, price or threshold assumptions. Complete it using `docs/PHASE_8_DEMAND_REVIEW.md`. `freeze --program <draft.json> --output <new-program.json>` validates and hashes its cohort, task selection, comparison and any owner-adopted continuation rules. `evidence-template --program <frozen-program.json> --output <new-evidence.json>` prepares every expected pilot/task and acceptance check with explicit unknowns.

`review --program <frozen-program.json> --program-hash <recorded-hash> --evidence <completed-evidence.json> --output <new-review-directory>` produces a readable `report.md`, exact input snapshots, calculated `report.json` and a file-hash manifest. `verify --bundle <review-directory>` checks all files and recomputes the report. Add `--previous <earlier-review-directory>` to retain the exact prior report hash and changed sections; a correction cannot silently replace the frozen cohort or thresholds. Old output paths are never overwritten. Hashes detect changes, not authority or truthful source content.

For a safe offline demonstration:

```sh
npm run review:agency:demand -- review \
  --program scripts/platform/fixtures/demand-program-v1.json \
  --program-hash 87c37835022b57728bcbb015b72227628ac65913aeabcc6f8567a2e46dd5c36f \
  --evidence scripts/platform/fixtures/demand-fixture-evidence-v1.json \
  --output /tmp/p11-demand-review-unique
npm run review:agency:demand -- verify --bundle /tmp/p11-demand-review-unique
```

The example is synthetic, including its reported acceptance checks; it never establishes actual acceptance. The tool does not query Supabase or accounting systems. Manually supplied records remain `imported_unverified`, even with favorable results. Keep real financial/source records in the client's access-controlled evidence location, not fixtures or source control. The tool records source hashes, client scope and availability times, preserves missing costs and failed tasks, separates pass-through amounts, includes review/remediation and all period onboarding/support costs, reports delivery denominators and uncertainty, and records evidence-linked demand decisions. No automated publishing, provider calls, money movement, training or permission changes exist. Existing CI discovers these offline tests without a new workflow.


## Connected synthetic client export and native workflow rehearsal

Read `docs/P11_CLIENT_LIFECYCLE_REHEARSAL.md` at the repository root for the exact tested scope and retained-copy limits. The Agency model planner is deferred. These developer tools never authorize a hosted release or a live agency action.

- `client_lifecycle.py export --database postgres --org <synthetic-org-id> --output <new-private-directory>` exports a named synthetic client, following ownership and foreign keys. Credentials are redacted in `client-data.json`; the distinct private snapshot is only for a disposable local restore. Use `verify --bundle <directory>` to check the data and any separately exported originals.
- In `apps/web`, run `scripts/client-lifecycle-storage.mjs export <bundle> unused <neighbor-property-id>` with the local environment to export actual knowledge-original bytes. Additional storage families require adapters and external references are not silently downloaded.
- `client_lifecycle.py offboard --database phase6_client_lifecycle_YYYYMMDD_suffix --snapshot <private-snapshot> --policy <reviewed-test-policy> --output <new-receipt> --rollback` first qualifies erasure and exact rollback. It refuses active-console writes, non-synthetic clients, holds, unelapsed retention, changed inventories and other database connections. Removing `--rollback` commits only in the disposable clone. It checks all foreign keys and unchanged unselected rows while the database is disconnected. This uses transaction-local trigger suppression, not a production cascade/retention implementation.
- The policy must name synthetic provenance, exact organization/source hash, export source hash, elapsed test retention, empty holds/pending writers, retained copies, `none_synthetic` provider copies, training exclusion and `erase_disposable_clone` mode. No real-client policy is inferred from this fixture.
- `scripts/client-lifecycle-quarantine.mjs <journey.json> <new-receipt>` stops supported native work and revokes only the synthetic source account/membership while retaining source rows as evidence. Run it before source-byte removal. Unknown active work or additional members require review.
- `scripts/client-lifecycle-storage.mjs remove <bundle> <committed-clone-erasure-receipt> <neighbor-property-id>` removes exact local original bytes through Storage after confirming the retained export and neighboring file. A saved intent makes absence verification retryable. Source database evidence remains explicitly retained; do not describe this as erasing every copy.
- `client_lifecycle.py restore-check --snapshot <snapshot> --receipt <erasure-receipt>` refuses restoration of an erased organization. Integrating this gate into a hosted backup workflow remains separate work.
- `sandbox_workflow.py --database phase6_client_lifecycle_YYYYMMDD_suffix --journal <new-private-file> register --org <org> --actor <fixture-operator> --property <property> --lead <lead> --expires-at <time-with-zone> --limit 2` registers at most one hour and two preparation effects. `operate --run <uuid> --operation prepare --property <property> --lead <lead>` saves source evidence; `advance`, `pause`, `resume`, `cancel` and `undo` use that same run. One shared journal is required for the shared budget. Native CRM preparation is attributed to the registered fixture operator; the journal labels deterministic automation. No model, provider approval or sending operation exists.

The two `apps/web/e2e/client-lifecycle*.spec.ts` browser tests are explicit retained rehearsals, skipped without `P11_CLIENT_LIFECYCLE_ARTIFACT_DIR`. Main journey first, followthrough second, then export/offboarding. Use a new synthetic client/evidence directory and local held-delivery preview; the recorded final fixture has been offboarded and its session removed. Do not point these tools at another Docker context, the active console for native execution/erasure, or hosted systems. Offline regression tests are included in ordinary platform test discovery.
