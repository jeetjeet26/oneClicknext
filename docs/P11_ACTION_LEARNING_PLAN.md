## Recommended default: no model training required

The owner's question is a request for the best path, not an instruction to perform pretraining, mid-training or RL. Build the agency first with capable existing models, grounded client context, explicit product APIs/tools, durable workflows, budgets/permissions and outcome evaluations. This can support bounded autonomy without training model weights. Use action records immediately for debugging, workflow discovery, regression evaluation and improving instructions/retrieval/tools.

Fine-tuning is optional and must demonstrate a recurring task gap plus a better measured quality/cost/intervention result than these simpler improvements. RL is a later optional research/optimization path requiring a defined decision problem and reliable reward evidence. Neither is a prerequisite for Phase 7. No foundation pretraining or mid-training project is currently needed. The staged methods below preserve future options while preventing training work from displacing complete products.

## What completion now means

Each product must have a complete input → decision → execution → result journey, an understandable operator interface, client/property isolation, truthful progress/errors, and a tested recovery case. Its meaningful user actions must be recorded across creation, edits, selection, requests, approvals/rejections, exports, cancellations, retries and corrections. Page/navigation observations are useful context but cannot prove a business action succeeded. Record the corresponding automatic actions too, identifying system/model/version and the human decision or standing permission that caused them.

A product is not complete because its page renders, a job reports success, or it emits events. The result must be persisted or acknowledged by its destination, and the action history must reconstruct the sequence without inventing missing outcomes. Client/provider acceptance remains an explicit release gate. Local fixture success is labeled as test evidence and excluded from production training examples.

## Action and episode contract

Use an append-only semantic event stream linked into bounded task episodes:

- Identity: event UUID, schema version, stable action/request UUID, episode/task UUID, parent/causal event, action attempt/job references, sequence and server timestamp; retain client observation time separately.
- Scope: organization, property/client and product; authenticated actor; human/system/model actor type and initiating human where known. Server derives identity and checks resource ownership.
- Decision context: authorized goal, versioned observation snapshot/reference available **before** the decision, relevant source/artifact versions, available/allowed actions and permission/budget state. Retain references to protected content instead of indiscriminate copies.
- Action: registered semantic verb, target resource, validated/redacted arguments, selected alternative and explicit decision reason when supplied. Capture structured rationale provided by the user or model; do not depend on hidden model reasoning.
- Lifecycle: observed/requested, accepted/rejected/modified, started, succeeded/failed/unconfirmed, cancelled, retried and reversed. A browser click records an observation. A server transaction records a mutation. A provider receipt records provider acceptance; recipient receipt requires separate evidence.
- Result: before/after state references or compact allowlisted changes, artifact/receipt references, error classification, duration, measured usage/cost with units and source; unknown values stay unknown.
- Human feedback: original proposal, edited replacement, accepted/rejected alternatives, reviewer, explanation, intervention and recovery effort. Approval alone is not a positive business outcome or an automatic preference pair.
- Outcome: verified metric definition/version, measurement window, observation date, baseline when actually available, attribution limits, maturity state, and links to the actions/episode. Keep immediate execution quality distinct from delayed commercial outcomes.
- Learning governance: provenance, fixture/production flag, training eligibility and permitted client reuse, redaction policy version, dataset inclusion/exclusion and deletion/tombstone lineage. Observation retention does not automatically authorize model training or cross-client pooling.

Execution-critical events must commit with the business mutation or via its transactional outbox. Browser observation transport must acknowledge persistence, retain stable IDs on bounded retry, surface collection gaps, and never silently create a success label. Retry events link to the original action while retaining distinct attempts. Every product needs a coverage manifest mapping user journeys, action names, capture sites, trust level and tests. Record credential rotation as an action without recording credential values; exclude passwords, cookies, access tokens and payment secrets. Resource fields use per-action allowlists.

## Learning sequence: pretraining, mid-training, post-training and RL

These are possible training stages, not four mandatory projects. Start with capable existing models, retrieval, explicit tools and deterministic controls. Measure this baseline before training model weights. Product action data can also improve routing, prompts, workflow design, scoring and anomaly detection without fine-tuning.

1. **Pretraining:** no foundation-model pretraining project is planned. The agency does not currently have the broad corpus, compute case or evidence of need. Revisit only if a measured business/research case supports it.
2. **Mid-training / continued domain training:** optional later work if evaluations show persistent domain/tool understanding gaps that retrieval, context, schemas and supervised examples do not solve. “Mid-training” is used inconsistently; define the exact objective and corpus before selecting it. Potential material is approved domain documentation, tool contracts and curated synthetic task environments. Raw clicks are not a domain language corpus; frequently changing client facts should remain grounded in current sources.
3. **Supervised post-training / imitation:** the first weight-training candidate. Convert curated successful human trajectories into observation → valid tool/action examples, including multi-step recovery and abstain/escalate examples. Preserve failures for diagnosis; do not imitate them as successes. Compare against the baseline on unseen episodes and clients. Iteratively collect expert corrections for states reached by the agent, rather than assuming human-only demonstrations cover every agent mistake.
4. **Preference post-training:** capture explicitly comparable proposals and human-selected/edited alternatives under the same context. Train a preference/ranking model or use DPO when the selected model and data support it. Keep reviewer disagreement and label confidence. Do not invent rejected alternatives from unrelated actions or treat every edit as proof the original was bad. DPO is a preference optimization method and does not require a separate reward-model-plus-online-RL loop.
5. **Offline / sandbox reinforcement learning:** optional after executable tasks, adequate coverage and trusted rewards exist. Train task selection/sequence/recovery policies from qualified trajectories and/or controlled environments. Historical behavior lacks many counterfactuals: do not assume offline success proves a new policy is safe or superior. Run bounded task simulations and shadow decisions before live execution; preserve deterministic permissions and budgets outside model control.
6. **Restricted online improvement:** only in Phase 7 after product/platform qualification and specific action permission. Start with reversible, low-impact scopes; require rollback, intervention and budget controls, measured rollout gates and a fixed comparison policy. Model changes do not expand standing permissions. High-impact sends, publishing and spending follow their own approved boundaries.

The learning target is a model/policy operating the products' explicit APIs/tools. Recording UI actions does not automatically train the Codex/ChatGPT model or grant access to its model weights. The exact trainable model/provider, dataset export destination and spend are selected from measured needs later; no training job or data upload is authorized by this planning document alone.

## Rewards and evaluation

Maintain separate outcome dimensions: correct authorized completion, factual/creative quality, destination-confirmed execution, recovery correctness, human intervention/time, latency, cost and delayed client value. Define product-specific rewards only after the underlying metrics are trustworthy. Treat permission violations, cross-client access, fabricated success and duplicate external actions as hard failures, not costs a high revenue score can outweigh. No rewards for extra sends, clicks or activity volume by itself.

Freeze evaluation sets before training. Split by episode and time, hold out clients/properties where allowed, and keep near-duplicate artifacts out of both train and test. Never include later outcomes or human corrections in the pre-action observation. Report sample sizes, coverage, uncertainty, client/product slices and long-tail failures. Keep test fixtures and simulated outcomes separate from real operational evidence.

Track propensity/action probabilities only where actually emitted by the behavior policy; ordinary human logs have unknown propensities. Use off-policy estimates only when their support and assumptions are satisfied. A conversion or lease after an action is not causal attribution by itself. Delayed outcomes mature on an explicit schedule; unobserved outcomes stay pending rather than becoming zero or success.

A model registry records base/model/provider, training objective, dataset manifest/hash, eligibility/redaction policy, tool/prompt versions, evaluation results, reward definitions and release/rollback identity. Each candidate must beat the current baseline on a preregistered task metric, remain within cost/intervention limits, and pass every safety/authorization regression. There is no invented universal sample-count threshold: the coverage and confidence needed depend on the action and its consequence.

## References

The design uses demonstration learning with iterative correction as a candidate approach ([DAgger research](https://arxiv.org/abs/1011.0686)); preference optimization can use explicit chosen/rejected pairs without a full RL loop ([DPO research](https://arxiv.org/abs/2305.18290)); learning from fixed historical trajectories has coverage and evaluation limits ([offline RL review](https://arxiv.org/abs/2005.01643)). These sources support method distinctions, not a claim that any method is already qualified on P11 data.
