# Phase 5 — recorded BI schedules

September 23, 2026. Local implementation and qualification; the complete BI product and Phase 5 gates remain open.

The BI Schedule control now manages the full local schedule lifecycle. Administrators and managers preview completed-period figures, create a paused schedule, edit it, schedule future reports, pause it, end an unresolved run and cancel it. Current property members can review schedules, complete paged history and per-recipient outcomes. Every change rechecks the actor, property and current schedule revision. Password-only sign-in remains the user policy.

New schedules are property-specific performance reports for all stored channels/accounts, with daily, weekly or monthly frequency, an explicit UTC hour and up to ten normalized unique recipients. Monthly dates are 1–28. Reports cover the previous calendar period, seven/thirty completed dates or month-to-yesterday. A month-to-date occurrence on the first day has no completed dates and records a skipped empty run. Preview uses today's completed period; each future occurrence uses its own scheduled date. No future facts are invented. Resuming always chooses a future occurrence; old backlogs are never automatically replayed. Runs more than 24 hours overdue require review.

Human commands retain their input and native result atomically with shared actions. A stable command identity belongs to its original actor. Lost responses can be checked after reopening the modal. Cancelling an unused request creates a tombstone that fences the delayed original; cancelling a completed request returns its actual result. Browser session storage contains only the request UUID, scoped by actor and property, and never recipient addresses, source facts or messages. Unavailable storage prevents an untracked mutation. Page fingerprints hold concurrent history changes for reload.

Each automatic occurrence retains its authorizing revision, exact configuration and recipients, source rows and source fingerprint, UTC period, and complete prepared message with a separate payload fingerprint. The email uses the same `bi-v1` metric calculation as the qualified console reports: cent-based totals, fractional provider-attributed conversions, undefined rates/zero-baseline changes shown as unavailable, source coverage, escaped source/user labels, full campaign/account identities and optional comparisons/campaign details. Every campaign is included or preparation is held when the complete email exceeds 512 KiB; nothing is silently truncated.

The worker claims an occurrence under a native row lock, holds its schedule, prepares the exact message, and grants a single start per recipient. Concurrent workers cannot claim the same occurrence. A replayed claim or delivery start never grants another provider call. Current author/property authority is checked again before each recipient. A start older than 15 minutes is fenced. Missing provider IDs, timeouts, lost acknowledgements or worker crashes remain unresolved. Later recipients stop after an uncertain result. Each destination has its own idempotency key, but there is no automatic retry at any age. Resend's documented key retention is 24 hours, so a key is not treated as perpetual deduplication: [Resend idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys).

Provider acceptance is recorded as acceptance, never as recipient delivery. A completed run advances only after every recipient has a persisted provider acceptance. Pausing, cancelling or ending a run marks unstarted recipients as not sent and already-started attempts as unknown. A later acknowledgement can preserve the original provider acceptance without reactivating a closed/cancelled schedule. Future scheduling never resends the closed run. Verified destination delivery/bounce/complaint receipts and account-specific provider reconciliation remain release work; the console states this limit explicitly.

Automatic results use the `bi.scheduler` service principal, separate from the human authorizing the schedule. Human create/edit/pause/resume/cancel/run-close/unused-cancellation decisions and system claim/start/acceptance/hold/finish/empty-period results are retained. All shared evidence stays training-ineligible. Acceptance is neither a commercial outcome nor a training reward.

Earlier `scheduled_reports` and `report_send_history` records remain readable in paged reference history. The new worker does not select them; earlier status labels are not upgraded into delivery proof. The former destructive DELETE and unrecorded PATCH API return a reload/recorded-decision response, and direct authenticated legacy schedule writes are revoked. No old schedule or history is deleted or automatically activated. New table access and RPC execution are service-only, with current actor checks in native decisions/reads. History follows property retention.

Real delivery remains paused. The cron endpoint requires its existing secret, the global outbound hold to be lifted, an explicit `BI_SCHEDULE_DELIVERY_ENABLED=true` qualification gate, and a configured provider/sender. No environment setting was enabled by this increment. Local verification uses synthetic recipients and a fake sender; no real email is sent. Hosted deployment/migration, real-provider acceptance/receipts, full destination authorization/retention policy and real-client acceptance remain separate gates.
